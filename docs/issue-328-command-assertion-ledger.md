## Diagnosis and closure

- The quickCapture trial initially watched the wrong RPC. The browser's persisted default
  destination is `root`, so `WorkController.performQuickCapture` calls `createItem`, not
  `quickCapture`. With a root preference fixture, the App shortcut was observed to dispatch the
  candidate through `createItem`, pass `{ text, parentId: null, afterId }`, reload the returned
  Outline item, and render/focus its editor. Temporary Event instrumentation showed
  `preventDefault=true` and `stopImmediatePropagation=true` at the `INPUT`; the window capture
  shortcut handler consumed the key before the component `onkeydown` callback. No production defect
  was found; all diagnostic code was removed from the final test.
- The LinkEditor flow is now observed end to end with the source row's displayed Work ID,
  `searchItems` request `contextItemId`, returned target result, chosen `FROM`/incoming
  direction/reason, enabled candidate button, exact createLink arguments, and the result link
  rendered. The earlier unscoped experiment did not assert source or target identity; the final
  check scopes the candidate to LinkEditor and validates both IDs. No production defect was found.
- D28 drives the actual history path: selected item → loaded snapshot list → selected snapshot →
  preview → `この状態を稿として保存` → accepted confirmation →
  `promoteRecoverySnapshot(snapshotId, workId, branchId, "confirmed")` → new revision shown in
  WorkLineage.
- All 41 original assertions are accounted for; no source-string guards remain.
