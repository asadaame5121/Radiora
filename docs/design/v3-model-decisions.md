## 1. #381：文書モデル・境界・同一性

### 決定

- LoroTreeの親を持たないBlockと子孫を一つの文書（Topic）とする。root自身がタイトル。
  独立したタイトルfieldは必須にせず、空/子なしの文書も許可する。
- root/通常Blockは同一ID体系。所属文書は親子関係から決まり、Hoist/Zoomは所属を変えない。
- root Enterは最初の子Blockを生成し、rootを分割して文書を増やさない。
  通常BlockはEnterで分割、Shift+Enterで改行する。
- 通常のindent/outdentは文書境界を越えない。
  通常Blockの部分木の文書切り出し、文書間移動は提供し、IDを維持する。
- Undo/Redoはworkspace共通履歴の操作順に従い、元の親子・順序・同一性を復元する。複製は新IDを発行する。
- Block IDはUUIDv7、workspace内で一意、削除後も再利用しない。
  移動・切り出し・Undo・復元で維持する。Loro TreeIDとは別の論理IDとして扱う。
- 正準内部リンクは `[表示名](radiora://block/<UUID>)`。
  ラベル変更と参照先の同一性を分け、本文リンクと型付きRelationを別機能にする。
- 通常削除は復元可能なTombstone。内部リンク/Relationは残す。
  完全削除は本文/タイトルを除去し、削除済みIDの最小記録とMissing参照を残す。
  中間Blockの削除で隣接Relationを自動接続しない。
- **完全削除はUndo不可とし、成功時にworkspace共通のUndo/Redo履歴をリセットする。**
  ゴミ箱からだけ実行し、通常Deleteキーへ割り当てない。対象の子孫を明示し、
  他の編集の取り消し履歴も失うことを確認表示する。外部の参照項目とその子を参照経由で連鎖削除しない。
- 完全削除は、workspaceの編集/Undo/Redo/autosave適用を止め、未保存入力を保存してから適用する。
  差分の耐久保存成功後、全履歴clearを完了してから成功表示・公開・操作再開する。
  未保存入力の保存失敗では削除へ進まず、削除適用後の保存失敗ではdirtyのまま後続操作を止めて再試行/復旧する。
  履歴だけを先に消したり、origin除外だけで既存履歴を残したりしない。
  状態・失敗処理・Alloy検査の境界は[完全削除とUndo/Redoの実装契約](purge-undo-contract.md)を参照する。
- v2の操作モデルを完全再現せず、蓄積された情報と参照関係を黙って失わせない。

### 通常削除・復元・参照先削除の採用契約

以下はユーザー承認済みの製品仕様。実装・実Loro検証の完了を意味しない。

#### 通常削除

- 通常削除は対象Blockと子孫をまとめてゴミ箱へ移す。本文・階層・論理IDを保持する。
  子を残す操作を通常削除へ混ぜず、必要なら別の明示操作として判断する。
- 初回はゴミ箱内の部分木を直接編集・移動しない。復元後に操作する。
- 復元するのは、その削除操作で新たに削除した範囲。以前から削除済みだった子孫は復元しない。 例:
  Cを削除してから親Bを削除した場合、Bの復元だけでCを復活させない。

#### 完全削除の対象集合

- 別の削除操作で作られたゴミ箱項目は独立して扱う。
  完全削除は選択したゴミ箱項目に含まれる集合だけを対象にし、
  元の親子関係をたどって別のゴミ箱項目を暗黙に含めない。
- 例: Bの子Cを先に削除し、その後Bと残る子Dを削除した場合、
  Bの完全削除対象はB/D。Cの本文・論理ID・ゴミ箱項目は残る。
  Cは元親Bを使えないため、確認のうえ独立文書として復元できる。
- 確認画面に対象集合を明示し、実際の本文除去・purged記録の集合と一致させる。
  ゴミ箱全体を空にする場合は、Cのような別項目も明示的に対象へ含める。

#### ゴミ箱からの復元

| 元の位置の状態                                     | 復元先                                         |
| -------------------------------------------------- | ---------------------------------------------- |
| 元の親が存在し、削除されていない                   | 元の親の下。兄弟位置も復元可能なら元の位置     |
| 元の親は使えるが、位置の目印となる兄弟がなくなった | 元の親の末尾                                   |
| 元の親がゴミ箱内または完全削除済みなどで使えない   | 確認のうえ、対象部分木を独立した文書として復元 |
| 元から文書root                                     | 文書rootとして復元                             |

- 独立文書として復元する場合も、対象の論理ID・本文・子構造を維持する。
- 親を暗黙に復元したり、無関係な親へ付け替えたりしない。
  親がゴミ箱内なら、親を先に復元してから対象の復元を再実行する選択もできる。
- ゴミ箱からの復元は新しい操作であり、共通履歴のUndoとは区別する。
  履歴Undoの位置復元を、時間が経過したゴミ箱復元のfallback規則で置き換えない。

#### 代表Blockと参照項目の削除

| 操作                | 参照項目・子構造への影響                                                       |
| ------------------- | ------------------------------------------------------------------------------ |
| 代表Blockを通常削除 | 部分木外の参照項目は残し、参照先がゴミ箱内と表示する。代表本文は通常表示しない |
| 代表Blockを復元     | 同じ論理IDへの参照として、参照項目の本文表示が戻る                             |
| 代表Blockを完全削除 | 部分木外の参照項目はMissing表示。参照項目自身の子構造は保持する                |
| 参照項目を通常削除  | その参照項目と、その配置に属する子孫だけを削除する。代表Blockは変更しない      |

- 代表の削除対象に含めるのは、その実際の部分木に属するものだけ。
  参照をたどって外部の参照項目やその子へ連鎖削除しない。
- 参照先がゴミ箱内で復元可能な状態と、完全削除・解決不能のMissing状態を表示上区別する。

### 参照chain・コピー時の参照対応の採用契約

- 初回は参照項目から別の参照項目へのchainを作らず、本文を所有する実体Blockを直接参照する。
  参照項目から参照を作成する場合も、その代表Blockへの直接参照にする。
  参照を作成しても、その配置の子構造をコピー・共有しない。
- コピーされたBlockと参照項目には新しい論理IDを発行する。
- コピー対象集合に参照先の実体Blockも含まれる場合、そのコピー先へ参照を張り替える。
  コピー対象集合外への参照は元の参照先を維持する。
- 本文の内部リンクと参照項目の参照先に同じ対応規則を適用する。 例:
  B→CをB/CまとめてコピーするとB'→C'、BだけのコピーならB'→元のC。

### Relationの対象・Topic投影の採用契約（2026-10-30）

以下はユーザーが推奨案を採用した製品仕様。旧データ変換の全仕様・実装完了とは区別する。

- 型付きRelationはroot・通常Block・参照項目の論理Block IDを両端に指定できる。
  参照項目へのRelationはその項目に属し、本文ownerへ自動で付け替えない。
  本文を共有する参照項目の作成（代表へ直接参照）と、型付きRelationのendpoint指定は別操作とする。
- カードはTopic root IDで識別し、Relationのendpointが属するTopicへ表示投影する。
  移動・文書切り出しでも元Relation ID/endpointを維持し、所属Topicと表示edgeだけを更新する。
- 同一Topic内のRelationはカード内関係とし、外部の世代計算へ使わず、カード上の自己edgeを作らない。
  元Blockの自己loop/循環は削除せず、カード内の循環として識別する。
- 同じカード間の複数Relationは集約表示し、元Relation ID集合と件数を保持する。
- Topic間投影の循環を「Topic投影上の循環」としてKnotへ分離し、元Blockグラフの循環とは区別する。
  循環メンバーだけを分離し、出入りする非循環Topicを巻き込まない。
- FROMの保存方向を変えず、派生元→派生先へ表示方向を正規化し、派生元を上・派生先を下に置く。
  世代/SCCは表示filter適用前の有効な世代進行Relationから計算する。
  filterは表示対象だけを変え、世代番号や循環membershipを変えない。
- ゴミ箱/MissingへのRelationは保持し、削除済み本文を表示せず、通常の世代計算から除外する。
  layout/世代/集約edgeは再生成可能な投影であり、元Relationへ書き戻さない。

### 折りたたみの採用契約（2026-10-30）

- 本文階層のfoldは、そのローカルユーザーのworkspace内UI設定としてSQLiteへ保存する。
  Loro文書/Relationとは別の設定領域に置き、文書共有やworkspace共通Undoの対象にしない。
  初回はアカウント/端末間同期を追加しない。
- keyはworkspaceと論理Block
  ID。同じBlockはOutline/Topicカード/各paneで同じ保存済みfoldを使い、再起動後も保持する。
  参照項目は自分のBlock IDで、固有の子構造のfoldを独立して持つ。
- 検索/リンク移動で対象を見せる一時展開は要求元paneだけに適用し、保存済みfoldを上書きしない。
- カード全体をタイトルだけにする開閉は本文foldとは別のUI設定とし、SQLiteの別keyで保持する。
- UI
  Controllerがlive設定と公開操作を一箇所で所有し、BackendのUI設定用API/保存adapterを通して永続化する。
  View・各paneからSQLiteへ直接書かず、本文foldのwriterとカード開閉のwriterをそれぞれ一箇所にする。
  設定保存失敗は未保存状態と再試行を示し、文書保存の成功/Undo履歴とは区別する。

## 3. #383：保存・Doc・履歴管理の検証

### 決定

- **単一workspaceに一つのLoroDoc**。Doc分割は現在の未決事項として扱わない。
- 文書/Block/Relationの正本はBackendのLoro。ControllerはBackend APIを使い、UI
  draft/focus/navigationのownerを維持する。ローカルfold/カード開閉は上記の別UI設定としてSQLiteへ保存し、Loroの正本を二重化しない。
- **初回v3のローカル編集はworkspace共通のUndo/Redo履歴を使う。**
  Backendが共通UndoManagerを所有し、別paneの直前操作もUndo対象になり得る。
  pane/sessionは履歴の選択単位にせず、要求元やfocus復帰の文脈として扱う。
  pane別の独立Undoは初回対象外とし、独自の選択的Undoは実装しない。
  文書モデル、単一Doc、保存方式はこの変更で変えない。
  根拠は[同本文Redoの比較記録](../../spikes/loro-purge/undo-research.md)。
  複数peerの任意順往復を保証するための方式ではなく、ローカル履歴を一つの順序にまとめる決定。
- SQLiteは最新1世代の全snapshot＋後続Updateを保存する。
  通常更新の成功は差分の耐久化までで、毎回全snapshotを待たない。
- snapshot置換と取り込み済み差分削除は同じtransaction。
  集約周期は差分量・件数・復元時間の測定から決める。内部履歴GCは別判断。
- 完全削除は過去履歴やbackupからの物理抹消まで保証しない。

### 共通Undoの操作単位・寿命の採用契約（2026-10-30）

- 同じBlockへの連続入力は入力間隔1秒以内を一まとまりとする。
  IMEは一回の変換確定、paste/cutは一操作、分割/indent/移動/削除/復元等の複合構造変更は一操作とする。
- Block切替、caretの明示移動、別paneの操作で直前のまとまりを終了し、その前後を結合しない。
  autosaveの実行だけではUndo単位を区切らず、保存commit単位と利用者のUndo単位を分ける。
- 別pane/別カードの操作をUndoしても画面を自動移動しない。取り消した対象・操作と「対象へ移動」を表示する。
  現在編集中の対象なら、有効性を確認して操作前のcaretへ戻す。
  明示的な対象移動は既存の共通navigationを通し、draft/focusのownerを履歴managerへ移さない。
- 初回は再起動でUndo/Redo履歴を終了する。文書とTombstoneは復元するが、永続Undoは提供しない。
- IME変換中はアプリUndoが介入せず、それ以外のキー/メニュー操作を共通入口へ集約し、native
  editorとの二重実行を防ぐ。 Undo/Redo前の未保存入力flushが失敗したら履歴操作を行わない。
- 完全削除の耐久化後に全履歴をclearする既存契約、保存失敗時に同じ差分だけをretryする契約は維持する。

### 残る実装・証拠

- crate固定、実効SQLite耐久性設定、writer/公開境界、保存失敗/retry/idempotency。
- UUIDv7生成器・衝突検出、削除済みID registry、履歴GCの具体方式。
- 単一Docでの1万件、編集履歴蓄積、メモリ、snapshot/復元、DB/WAL実容量。
- 実Loroのmove/cut/undoをPoCで検証する。AlloyモデルでLoro自体が検証済みとはしない。
- 共通履歴での複数pane由来の編集、Tree移動・削除復元・複合command、保存失敗/retry、
  完全削除後の履歴resetを検証する。既存の複数manager PoCの成功を、そのまま合格証拠へ流用しない。

モデル決定#381と、最小fixtureを使う保存技術PoCは並行できる。
単一Doc方針が実測で成立しない場合は、勝手に分割せず決定の見直しとして報告する。

共通履歴の[追加Rust fixture検証](../../spikes/loro-purge/shared-undo-results.md)では、
複数pane由来の本文編集、Tree移動/切り出し/削除復元、複合split、SQLite保存失敗/retry、

製品UI・focus/IME、crash復旧、規模性能、共通履歴版Alloyは未検証であり、#383全体の完了とはしない。

## 7. 細部の設計判断と変更コスト（2026-10-30）

ユーザー方針: 今後の設計の細部はGPT推奨案で進める。通常のUI/実装判断ごとに確認を挟まず、
理由・変更範囲・検証を記録する。既決契約や情報保全を変える、または変更コストが大きい判断では影響と選択肢を明示する。
この方針は既存のrelease/利用切替/撤去や破壊的操作の承認を代替しない。

| 判断                                  | 後から変える費用                         | 変更しやすくする境界                                                      |
| ------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------- |
| カード表示・集約・世代配置            | 小〜中。再計算とUI回帰が中心             | 元Block/Relation IDとendpointを保存し、layout/世代/集約edgeを書き戻さない |

| Relationの対象同一性・削除/参照の意味 | 大。既存データの解釈・互換性に関わる     | 論理IDを維持し、変更時は明示migration/互換性fixtureを用意する             |
