# 最近編集したメモの性能是正契約（P4）

この文書は実装前に合意する契約であり、P4のmain反映完了を示すものではない。 `rankRecentEditedItems`
の正本は入力snapshotで、結果は派生表示である。

## 維持する表示契約

- stashの表示場所を除外し、同じWorkの候補は最上位の表示場所にまとめる。
- `updatedAt`の降順、不正日時は0、IDの`localeCompare`、同値なら入力順で順位を決める。
- Workの候補を後から置換しても、勝った表示場所の入力順を維持する。
- 既定件数は6件。入力配列・項目を変更せず、元の項目への参照を返す。
- 10,000個の異なるWorkと大量の重複表示場所で、従来の全体sortと結果を比較する。

## 後続実装の契約

通常の固定件数kでは全体sortをやめ、走査をO(N × k)、選抜状態をO(k)とする。
stash除外のSetは別途O(S)を要する。Infinityを指定する全件取得では固定kの性能を保証しない。

limitの正規化は最適化と分けてレビューする。NaN・0以下は0件、正の小数は切り捨て、
Infinityは全件とする。負数をArray.sliceの末尾除外として扱う現行挙動はここで明示的に変更する。

## マージ順と検証

テストとこの文書はそれぞれmainをbaseにでき、P3のSQLite積み上げを必要としない。
現行契約の回帰テストを先にマージし、limit正規化、bounded top-kの順に実装する。
先行テストは未実装APIや性能の時間閾値を要求しない。テストのskip・ignoreは用いない。
limit変更の回帰は正規化PRで追加し、先行回帰を後続実装でも再実行する。
