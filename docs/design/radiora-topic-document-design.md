# Radiora 基軸設計：Topicルートとアウトライナー文書

- 作成日：2026-10-12
- 状態：文書の単位・タイトル・編集操作・内部参照を決定。その他は設計原則、採用候補、未決事項として整理。
- 元となる議論：[基軸設計の整理](chatgpt-conversation://6aca2b7f-2264-83ee-8dd0-0ad416738edd)
- 対象：文書の単位、編集操作、参照、既存モデルからの段階的移行

## 1. この設計の要点

Radioraでは、最上位ブロックを文書のタイトル兼Topicルートとし、その子孫全体を一つの文書として扱う。文書は「タイトルと本文」を持つが、本文の編集にはブロックの階層を使う。

編集UIとアウトライナー操作は維持する。Tab、Enter、階層変更、折りたたみなどによって考えを組み立てる操作を、文書モデルの変更と引き換えに失わない。

文書内のブロックにもリンクできるようにし、文書単位の整理と、内部の一点を参照する能力を両立させる。安定したブロックIDは実現案として扱い、形式や同一性の規則は未決とする。

work /
occurrenceを基軸に据え続ける必要があるかを再考する。ただし、既存実装や既存データを一括で置き換える方針ではなく、実際の依存関係を調べたうえで段階的に移行する。

## 2. 背景

以前の「1行＝1項目＝一つの知識」という捉え方では、編集のために区切った行と、知識としてまとまりを持つ単位が重なっていた。今回の変更では、文書（Topic）を知識をまとめる単位、ブロックを編集・参照の単位、アウトライナーを文書を構築する編集インターフェースとして分ける。

実身・仮身やwork /
occurrenceの問題は、概念が複雑だったことだけではない。通常の階層編集まで「内容の同一性」と「配置の同一性」の区別に巻き込まれ、日常の記述を理解・操作する負担になったという点にある。基本的なアウトラインを単純な親子関係として扱い、共有内容や複数配置は必要性を確認した機能として別途考えることが、今回の簡素化の方向性である。これは議論から得た設計原則であり、既存機能の廃止を決めるものではない。

たとえば、次のアウトラインは、タイトルと本文を持つ普通のメモとしても読める。

```text
・Denoとは
    ・JavaScriptランタイムの一つ
    ・ライアン・ダールが作った
```

この形を自然に文書として扱うなら、最上位項目をタイトル、子孫を本文とみなせる。一方、階層を使って書く操作には価値がある。したがって、文書の概念を導入することと、アウトライナー編集をやめることは切り離して考える。

また、参照したい対象は文書のタイトルだけではない。「精神分析」という文書内の「フロイト」に、別の文書からリンクしたい場合がある。内部ブロックへの参照は必要であり、文書単位にまとめても残す。

### 議論の根拠と確定度

参照会話から確認できたユーザー発言、初回の依頼、および今回ユーザーから提示された補足・指摘を根拠とする。過去のアシスタント回答本文は直接取得できていないが、その不足を今回の補足で埋めている。補足に含まれる議論の理由や設計案を記録することと、その案を採用済みと扱うことは区別する。

第5章は設計判断の理由を記録するADRとして、明示的な決定、議論から得た設計原則、採用候補を分ける。移行手順、判断基準、検証項目も提案である。Radioraのコードやデータ形式を調査した結果ではなく、既存実装との対応は別途確認する。

## 3. 目標

1. ユーザーが文書のまとまりを理解できる基軸を作る。
2. タイトルと本文を持つメモとして読みつつ、階層で編集できるようにする。
3. 文書内の任意のブロックを、編集や並べ替えに耐える安定した参照対象にする。
4. work / occurrenceの役割を必要性から見直し、概念と実装の複雑さを減らす。
5. 既存データ、リンク、編集体験を守りながら段階的に移行する。

## 4. 非目標

- この文書だけで新しい保存形式やID形式を確定すること。
- 既存のwork / occurrenceを直ちに削除すること。
- アウトライナーを通常の段落エディタへ置き換えること。
- リンク、埋め込み、複数配置を同じ操作としてまとめること。
- Relation、版管理、系統管理の全機能を同時に設計・実装すること。
- Markdownを唯一の保存形式にすること。本書の形式と製品の保存形式は別の問題である。

## 5. 設計判断の記録（ADR）

### 5.1 判断の背景と理由

**編集単位と知識単位を分ける。**
一行の長さや分割位置は編集の都合で変わる。それを知識の単位と同一視すると、階層編集が知識の独立や同一性の判断まで背負う。文書（Topic）が知識のまとまりを担い、ブロックが編集と内部参照を担うことで、文章を組み立てる操作と、知識を整理する操作を区別できる。ブロックごとに独立した知識であることを要求しない。

**通常の階層編集を共有モデルから切り離す。**
実身・仮身モデルから得た教訓は、内容と配置の同一性を区別する仕組みを通常編集の前提にしないことである。基本の親子関係をまず理解できるようにし、複数配置や共有内容は具体的な用途が確認されたときに検討する。既存の共有の意味を失わせてよい、という判断ではない。

**文書内部の構造と文書間の関係を分ける。**
「Denoとは」の中に「Node.jsとの比較」があることは本文の構造であり、「Denoとは」が別の文書から派生したことは文書間の由来である。関連、派生、版系統を本文の親子関係で代用しない。この区別をもとに、Radioraの系統樹が何を表すべきかを再検討する。系統樹の対象、Relationとの分担、版の表現は未決である。

**原稿ビューを同じ文書の別形式として考える。**
文書というまとまりができれば、原稿ビューを「アウトラインから文章を生成する特殊機能」だけで説明する必要はなくなる。同じ文書に対する別の表示・編集形式として扱える可能性がある。これは採用候補であり、双方向編集、変換規則、同期方法を決めたものではない。

### 5.2 明示的な決定

| 項目       | 決定                                                                                 |
| ---------- | ------------------------------------------------------------------------------------ |
| 文書の単位 | 最上位ブロックとその子孫を一つの文書とみなす。                                       |
| タイトル   | タイトル自体もアウトラインのブロックであり、最上位ブロックを文書タイトルとして扱う。 |
| Topic      | 最上位ブロックがTopicルートを兼ねる。                                                |
| 編集UI     | 現在のアウトライナーとしての編集UIを維持する。                                       |
| 編集操作   | Tab、Enter、階層変更、折りたたみ等を維持する。文書境界をまたぐ場合の意味は未決。     |
| 内部参照   | 文書内部のブロックを参照できることが必要。ID形式や操作ごとの同一性は未決。           |

「操作を維持する」という決定は、ルートのインデントや文書統合を含む全ケースの振る舞いが決まったことを意味しない。文書境界に影響する操作は、通常の本文編集とは別に仕様を詰める。

### 5.4 判断の効果と代償

期待する効果は、知識をまとめる単位を文書として説明でき、通常の編集で内容と配置の同一性を毎回意識せずに済むことである。内部参照の必要性を残すため、文書化しても細かな参照先は失わない。

一方、文書境界をまたぐ階層変更や、既存の共有内容の扱いは新たに明確化する必要がある。原稿ビューや系統樹も同じ基軸から再検討できるが、この判断だけで各機能の仕様が完成するわけではない。

## 6. 概念モデル

### 6.1 ブロック

ブロックは、内容を持ち、親子関係と兄弟順序によってアウトラインを構成する編集単位である。

内部参照の実現案として、安定IDによってタイトルや本文の文字列、表示位置から独立して参照する方式を検討する。IDの採用方式、データベースのキー、URL形式は未決である。

### 6.2 Topicルート

Topicルートは最上位ブロックであり、その内容を文書タイトルとして扱う。子孫を持たないルートも、本文が空の文書として扱える。

採用候補として、文書構造の最上位と、ズームによって画面上の先頭になる内部ブロックを区別する。ズームを表示範囲の変更として扱い、文書境界を変えない案があるが、その採否と振る舞いは未決である。

Topicという概念が独立した保存レコードを必要とするか、ブロックの位置から導出できるかは未決である。

### 6.3 文書

文書は、Topicルートとその子孫からなるまとまりである。本文の範囲はルートの子孫であり、ルート自体はタイトルを担う。

```text
ワークスペース等の文書一覧（具体的な管理方式は未決）
├─ TopicルートA = タイトルA
│  ├─ 本文ブロックA1
│  │  └─ 本文ブロックA1a
│  └─ 本文ブロックA2
└─ TopicルートB = タイトルB
   └─ 本文ブロックB1
```

基本の階層を単純な親子関係として扱う案では、各ブロックは一つの親子ツリーに属し、最上位の祖先から所属文書を理解できる。この具体的な所属規則は設計案である。既存の複数配置をどう対応させるかは未決であり、同じ内容を持つ既存データを勝手に独立ブロックへ変換しない。

### 6.4 参照

リンクは、対象のブロックを指す参照である。リンク元とリンク先が同じ文書に属する必要はない。

安定参照の案では、タイトル変更、本文編集、兄弟順序変更でリンクが失われないことを目指す。これは提案する判断基準であり、IDの詳細仕様を確定するものではない。文書をまたぐ移動時のID継承や、削除・復元・複製時の扱いは未決事項として詰める。

リンクを置くことと、対象の内容をその場に埋め込むことは区別する。埋め込みの表示範囲や編集権限は、この基軸設計から自動的には決まらない。

### 6.5 work / occurrenceとの関係

今後の基軸は「Topicルート／文書／ブロック／参照」で説明することを目指す。work /
occurrenceをそのまま新しい名前に置き換えるのではなく、各役割を確認する。

- 内容の共有が必要な機能は何か。
- 配置ごとに異なる状態が必要な機能は何か。
- 通常のブロックリンクで足りる機能は何か。
- 埋め込みや版管理のために、独立した同一性が必要か。

既存の役割が新モデルで表現できると確認するまでは、互換層や旧データを残す。work＝文書、occurrence＝ブロックという一対一対応は、この時点では決めない。

### 6.6 文書内部の階層と文書間の関係

| 関係               | 例                                                 | 意味                                   |
| ------------------ | -------------------------------------------------- | -------------------------------------- |
| 文書内部の親子関係 | 「Denoとは」の子に「Node.jsとの比較」を置く。      | 本文を構成・編集するための階層。       |
| 文書間の関連       | 「Denoとは」と「Node.jsとは」を関連付ける。        | 独立した知識のまとまり同士のつながり。 |
| 文書間の派生       | 「Denoとは 改稿案」を元の文書から作る。            | 文書の由来や派生。                     |
| 版・系統           | 同じ文書の旧版と改訂版、または改稿案の分岐を追う。 | 時間や由来に沿った関係。粒度は未決。   |

本文の階層の変更を、派生や版の変更として自動的に解釈しない方向で検討する。系統樹は何の由来を示すか、文書の派生と同一文書の版を同じ構造で表すか、ブロックの履歴も対象にするかを別途決める。

### 6.7 原稿ビュー（採用候補）

アウトライナーと原稿ビューを、同じ文書に対する異なる表示・編集形式として扱う案がある。前者はブロックの階層で構築する形式、後者は文章として読む・書く形式である。原稿ビューのために独立した知識単位や別の原稿データを必ず作る、という前提は置かない。

ただし、別形式という捉え方から双方向編集が自動的に成立するわけではない。まず表示のみとするか、編集も可能にするか、文章の段落や見出しをブロック・階層へどう対応させるかは未決である。生成による文章化を残す場合も、同じ文書の表示と、内容を変える生成処理を区別して検討する。

## 7. 具体例

### 7.1 タイトルと本文

```text
Denoとは                         ← Topicルート／タイトル
├─ JavaScriptランタイムの一つ    ← 本文
└─ ライアン・ダールが作った      ← 本文
```

一つの文書として読むと、タイトルは「Denoとは」、本文は二つの子ブロックとなる。編集ではEnterで項目を増やし、Tabで階層を作り、折りたたみで表示を整理する。

これらの操作について、ルート上のEnterや最上位へのアウトデントが何を作るかは別途決める。

### 7.2 文書内部へのリンク

```text
精神分析                         ← Topicルート
└─ フロイト                      ← 参照したい内部ブロック
   └─ 生涯や思想についてのメモ

最近読んだ本                     ← 別のTopicルート
└─ 『ユングと[[フロイト]]』
```

ここで参照したいのは「精神分析」文書全体ではなく、その中の「フロイト」である。安定したブロックIDへリンクを解決するのは実現案の一つであり、詳細仕様は未決である。

上の二重角括弧は記述意図の例であり、確定した入力構文ではない。同名候補の選択方法、表示ラベル、保存形式は未決である。文字列だけで参照先を一意に決められるとは限らない。

### 7.3 分割・統合の検討例（採用候補）

「精神分析」の中の「フロイト」とその子孫を独立文書へ分割したい場合、内部ブロックを新しいTopicルートへ昇格する操作が考えられる。

逆に、独立した文書を別の文書の子へ入れると、旧タイトルは内部ブロックになる。文書の統合に相当する可能性があるが、単なる表示整理と区別が必要である。

昇格・分割・統合は採用候補であり、操作の提供自体を確定していない。採用する場合の既存リンク、Topic固有の情報、履歴の引継ぎも未決である。

| ズーム             | 機能の採否。採用時の表示ルート、タイトル、所属表示、戻る操作、編集範囲。                                   | 表示範囲と文書境界を混同しない。                           |
| 原稿ビュー         | 同じ文書の別形式として扱う案の採否。表示のみか双方向編集か。段落・見出し・階層・ブロック参照・Undoの対応。 | 別表示と内容生成を区別し、編集時の構造や参照の欠落を防ぐ。 |
| 折りたたみ状態     | 文書・配置・ユーザー・画面のどこに保存するか。移行時の引継ぎ。                                             | 内容と表示状態を適切に分離する。                           |
| コピー・外部入出力 | コピー時の新ID、リンクの再対応、インポート時の衝突、エクスポートでの参照保持。                             | コピーと移動の同一性を区別する。                           |

IDの方式として内容ハッシュを採用することは決めていない。編集によって変わるハッシュをそのまま参照IDにすると安定性の要件に合わないため、変更検出用のハッシュと参照用IDは分けて検討する。

## 9. 段階的な移行案

以下は実装調査前の提案であり、採用済みの工程ではない。未決の操作や機能は仕様と採否を決めてから対象に含める。段階ごとの完了条件案を確認し、次に進む。保存形式の変更を最初の前提にしない。

### Step 1：現状の依存関係を確認する

work /
occurrenceの保存、作成、編集、移動、削除、リンク解決、表示状態、履歴、入出力を調べる。複数配置や共有編集が現に使われているデータも把握する。

成果物は、既存概念の役割と新モデルの対応表、およびそのままでは対応できないケースの一覧とする。既存データのバックアップと復元手順も確認する。

完了条件：影響する呼び出し元、テスト、フィクスチャ、設定、外部入出力の範囲と、情報を失う可能性があるケースが分かっている。

### Step 2：既存構造の上に文書の読み方を導入する

既存データを読み取り、最上位ブロックと子孫を文書として表示する。タイトル兼Topicルートという説明をUIへ反映する。

ここでは旧保存形式を維持できるかを先に検討する。複数配置などの対応不能ケースは識別して扱いを保留し、見た目に合わせてデータを破壊的に正規化しない。

完了条件：通常の文書を新しい概念で読め、既存の編集操作が維持されている。

### Step 3：安定したブロック参照を成立させる

既存IDが要件を満たすなら再利用する。不足する場合にだけ新IDや旧IDとの対応表を導入する。旧リンクを解決する互換経路を用意する。

完了条件：タイトル変更、本文編集、並べ替え、再読込の後も同じブロックへリンクできる。削除された参照先も誤った別ブロックへ解決しない。

### Step 4：文書境界に関わる操作を確定する

ルートのインデント、本文のアウトデント、分割、統合、文書間移動を仕様化する。ID、リンク、付随情報、履歴、Undoの扱いをセットで決める。

完了条件：各操作の前後で、どの文書に何が属するか説明でき、必要なデータを保持して取り消せる。

### Step 5：新モデルへ保存・更新経路を移す

必要と確認された範囲で保存形式を変更する。移行の中断・再実行、旧形式の読取、ID対応、バックアップからの復元を検証する。

旧経路と新経路を併用するなら、どちらを正とするかを明示する。二重書込みは必要性を確認してから採用し、整合性維持の仕組みを無条件に増やさない。

完了条件：代表データで内容、順序、階層、参照、必要な表示状態を保てる。移行できないデータが明示され、利用者の判断なしに削除されない。

### Step 6：不要になった旧概念を削減する

新モデルで役割が代替されたwork /
occurrenceの経路を削除する。必要な共有・配置・履歴の機能が残る場合は、その用途へ限定する。

完了条件：旧経路への依存と旧データの扱いが確認済みで、互換機能を外せる根拠がある。一括削除を移行の成功条件にしない。

## 10. 検証方針

実装時には、次の代表ケースを小さな固定データで検証する案とする。未決の機能は採用された場合に検証対象へ含め、以下の項目だけで採用が決まったとは扱わない。

- 空の文書、子を持つ文書、深い階層、同名タイトル。
- Enter、Tab、階層変更、折りたたみの既存操作とフォーカス・選択状態。
- 内部ブロックへの文書内リンクと文書間リンク。
- タイトル変更、本文編集、並べ替え、再読込後のリンク解決。
- 分割・統合・移動とUndo後の所属、ID、リンク、付随情報。
- 削除・復元・複製時の参照とIDの扱い。
- work / occurrenceの複数配置や共有内容を含む旧データ。
- 移行中断と再実行、旧リンクの解決、バックアップからの復元。
- ズームを採用する場合の所属表示と文書境界、折りたたみ状態。
- 文書内部の階層変更と、文書間の関連・派生・版系統が混同されないこと。
- 原稿ビューを採用する場合の階層・ブロック参照の保持。双方向編集を採用する場合は往復編集とUndo。

単純な件数一致だけで移行成功と判断しない。内容、親子関係、順序、参照先、共有の意味が維持されるかを確認する。本書作成時点ではこれらの実装検証は行っていない。

## 11. リスクと対応方針

| リスク                                               | 対応方針                                                       |
| ---------------------------------------------------- | -------------------------------------------------------------- |
| ルートのインデントが意図せず文書統合になる           | 境界操作を仕様化し、操作結果が分かる表示と取り消しを用意する。 |
| 移動や再採番でリンクが切れる                         | 安定IDと移行対応表を検討し、既存リンクを含めて検証する。       |
| 複数配置を独立コピーへ変え、共有編集の意味が失われる | 共有の実利用を調べ、移行可能性を確認するまで旧表現を保持する。 |
| 文書化によってアウトライナー操作が窮屈になる         | 本文の操作を維持し、境界ケースだけを明示的に扱う。             |
| ズーム先を文書ルートと誤認する                       | 所属文書と表示範囲を区別して示す。                             |
| Relationや版管理を先に盛り込み、複雑さを再導入する   | 必須要件から判断し、未決機能を基本編集の前提にしない。         |
| 旧・新更新経路の併存で内容が食い違う                 | 正とする経路と切替条件を定め、併存期間を限定する。             |

| 原稿ビューで階層や参照が失われる                     | 構造との対応を定め、表示と編集の採否を分けて検証する。         |
| 系統樹が本文の階層と混同される                       | 内部構造と関連・派生・版系統の意味を区別し、対象を明示する。   |

## 12. 次に決める順序

1. 文書境界に関わる操作：ルート移動、インデント、アウトデント、統合、分割、Undo。
2. 同一性と参照：ブロックID、Topicの同一性、複製・削除・復元、旧リンク。
3. 既存実装との対応：work / occurrenceの依存と複数配置、データ移行。
4. 表示と参照の体験：ズーム、リンク候補、埋め込み、折りたたみ状態、原稿ビューと双方向編集の採否。
5. 文書間の関係モデル：Relation、版管理、系統管理、系統樹の役割。

明示的な決定は、最上位項目と子孫を一つの文書にすること、タイトル自体もアウトラインのブロックとして扱うこと、アウトライナー編集を維持すること、内部ブロックへの参照を可能にすることである。設計原則は判断の理由として残し、ID、ズーム、昇格・分割、原稿ビュー、系統樹などの具体案は採用候補・未決事項として検討する。
