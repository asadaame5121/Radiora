# Radiora v2 製品方向性・機能仕様

## 1. この文書の目的

この文書は、Radiora v2のPoC完了後に実装する機能と、実装しない機能の境界を定める。
個別画面の詳細設計ではなく、次の事項を共有するための基準である。

- Radioraが何を扱うアプリケーションなのか
- 既存のアウトライナーやメモアプリから何を輸入するのか
- 実身・化身、異本、Branch、型付きリンクをどう共存させるのか
- どの順序で実装し、どこから実使用による改善へ移るのか
- 汎用ノートアプリ化を避けるため、何を実装しないのか

本書に記載した中核機能を実装した後は、機能を先回りして増やす段階を終え、Radiora自身を
継続的に利用するドッグフーディングへ移る。以後の改善は、実際の利用で観測された摩擦、
データの育ち方、検索や系統表示の破綻を根拠に決める。

> [!important] 開発フェーズの出口
> 本書の中核機能を実装し、`cd v2 && deno task verify`が成功した時点で、仮説駆動の機能追加から
> 実使用駆動の改善へ移行する。検証が失敗している状態を完了としない。

## 2. 製品の定義

Radioraは、日々生じる短い着想から長文の稿までを同じ「思索」として保存し、その仮配置、
意味関係、改稿、派生、異本を追跡するローカルのアウトライナーである。

一般的なマインドマップが概念の空間配置を、通常のアウトライナーが現在の階層構成を、
バージョン管理が復旧可能な変更履歴を主に扱うのに対し、Radioraは次の連続した過程を扱う。

1. 関係を決め切らないまま思索を書き置く
2. アウトライン上で暫定的に配置する
3. タグや弱いリンクで関係の候補を残す
4. `FROM`、`SUPPORT`、`VS`などで意味を確定する
5. 改稿を上書きではなく別稿・異本として分岐させる
6. 系統樹から思索と本文の伝承を読む
7. 必要な思索を長文へ編成し、外部形式へ出力する

Radioraは日記専用アプリでも、Word代替でも、形式論理エディタでもない。

> **一本の生きたアウトラインへ日々書き足し、関係と異本を育て、必要なときに長文へ結実させる
> 思索環境**

を目指す。

## 3. 設計原則

### 3.1 関係を早く決め過ぎない

アウトラインのインデントは、包含、派生、近接、作業上のまとまりのいずれであるかを
即座に確定しなくてよい。意味を断定する関係と、暫定的な配置をデータモデル上で分離する。

### 3.2 日付は親ではなく座標

日付ノードを毎日自動生成して思索の親にしない。作成日時と更新日時は検索、Todayビュー、
系統樹の時間軸に使う。日記を書きたい利用者は、通常のアウトラインとして日付階層を自由に作れる。

### 3.3 改稿は破壊ではなく分岐

復旧用の編集履歴と、意味のある稿・版を区別する。全面改稿は元稿を上書きせず、別Branchまたは
独立した実身として開始できる。

### 3.4 配置と同一性を分ける

一つの思索を複数の原稿やアウトラインへ配置しても複製しない。実身と化身を分離し、
同じ本文を複数の文脈から参照・編集できるようにする。

### 3.5 系統は木に限定しない

複数の稿を合わせた混成稿や複数の思索を継承した派生を許す。基礎構造は複数親を持てる
有向非巡回グラフ（DAG）とし、画面では必要に応じて木へ投影する。

### 3.6 候補と確定を分ける

検索、語彙一致、タグ、AIなどが提示する関係候補を、自動的に意味リンクへ昇格させない。
根拠を示し、採用、却下、保留を利用者が決める。

### 3.7 出口を持つが、組版を抱え込まない

論証の設計、構成、組み替え、連続原稿化まではRadioraで行う。最終校閲、共同レビュー、
ページ組版はObsidian、Wordなどへ渡す。

### 3.8 可搬性を失わない

Markdown、OPML、JSONを役割別に出力する。Radiora固有のグラフ情報をMarkdownだけに
無理に押し込まず、完全バックアップ形式を別に持つ。

## 4. 中核ドメインモデル

現行の`OutlineItem.parentId`は、アウトライン配置と`FROM`系譜を同時に表している。
今後はこの多重責務を分解する。

### 4.1 実身（Work / Node）

思索または文章が「同じもの」であるという同一性を表す。

```ts
interface Work {
	id: string;
	createdAt: string;
	updatedAt: string;
}
```

本文は現在の`OutlineItem.text`からRevisionまたはWorking Copyへ移す。ノードを短い箇条書きと
長文文書へ型分けしない。一行の着想も数千字の文章も同じ実身として扱う。

### 4.2 Revision（稿・版）

ある時点で成立した、変更不能な本文の版を表す。

```ts
interface Revision {
	id: string;
	workId: string;
	text: string;
	parentRevisionIds: string[];
	kind: "checkpoint" | "edition" | "merge";
	createdAt: string;
	message?: string;
}
```

- `parentRevisionIds`は複数を許し、混成稿を表現できる
- 確定後のRevision本文は変更しない
- DiffはRevision間で計算する
- 重要なRevisionだけを全体系統樹へ表示する

### 4.3 Recovery Snapshot（復旧スナップショット）

クラッシュ、誤編集、Undoのための細粒度履歴である。Revisionとは分離する。

Snapshotの生成と保持は差し替え可能な内部`SnapshotPolicy`へ分離する。初期既定値は次のとおり
とし、細かな時間設定を利用者向け設定画面へ露出しない。

#### 作成

- 編集停止から10秒後にSnapshot候補を作る
- 同一Working Copyでは最短1分間隔とする
- 前回から内容が変わっていない場合は作らない
- 本文はWorking Copy単位、配置やリンクなどの構造変更はTransaction単位で保存する
- 破壊的操作、Import、schema migration、restore、mergeの直前は間隔に関係なく作る
- 復元の直前にも現在状態を保存する

#### 保持と間引き

| 経過期間 | 保持粒度 |
|---|---|
| 7日以内 | 全件 |
| 8日から30日 | 1時間につき代表1件 |
| 31日から1年 | 1日につき代表1件 |
| 1年超 | 1か月につき代表1件 |

代表は、保護対象を除き、その時間帯の最後のSnapshotを優先する。内容ハッシュを保持し、
初期実装では復元の独立性を優先して全文Snapshotを基本とする。容量と復元時間を実測した後、
圧縮または差分を検討する。

#### 保護

- 利用者が明示的に保護または命名したSnapshotは間引かない
- Import、schema migrationの直前Snapshotは自動的に保護する
- 通常の削除、移動などの操作境界Snapshotは30日後に通常の間引き対象へ戻す
- Revisionの生成元として参照されるSnapshotは、Revisionが存在する間は保護する

「すべての履歴から完全に消去」では、消去対象の本文をSnapshotへ複製しない。
完全消去と復旧可能なゴミ箱操作の違いは[[#4.8 削除とゴミ箱]]に従う。

#### 復元とRevisionへの昇格

復元では履歴を巻き戻さない。現在状態をSnapshotへ保存し、対象との差分をプレビューした後、
過去の内容を新しい現在状態としてWorking Copyへ適用する。復元後も中間のSnapshotを残す。

任意のSnapshotは「この状態を稿として保存」によりRevisionへ昇格できる。Recovery Snapshotは
通常の系統樹には表示せず、昇格したRevisionだけを版系統の対象とする。

初期既定値は永久不変の正解とは見なさない。ドッグフーディングではSnapshot件数、保存容量、
実際に復元された時点の古さ、復元成功率、間引き後に必要な状態が残っていたかを測定し、
`SnapshotPolicy`を改訂する。

### 4.4 Branch

同じ実身の中で進行中の稿の系統を指す、名前付きポインターである。

```ts
interface Branch {
	id: string;
	workId: string;
	name: string;
	headRevisionId: string | null;
	createdAt: string;
	promotedAt?: string;
	archivedAt?: string;
}
```

最低限`main`を持つ。新規WorkはRevision未確定のWorking Copyだけを持てるため、
最初の「版として残す」までは`headRevisionId`を`null`とする。「全面改稿」「短縮版」
「公開版」などを並行して維持できる。

### 4.5 Working Copy（作業稿）

Branch先端から編集中で、まだRevisionへ確定していない本文である。

- 自動保存の対象
- Branchごとに独立する
- 複数の作業稿をペインで同時に開ける
- 「版として残す」でRevisionへ確定する
- 「別稿として書き直す」で新Branchと作業稿を作る

Working Copyの自動保存とRecovery SnapshotはRevisionを作らない。時間経過、編集停止、
アプリ終了、Branch切替、通常のexportでもRevisionを自動確定しない。

Revisionは利用者が「版として残す」を実行した場合だけ作る。固定Revisionを必要とする
複合操作は、版保存が含まれることを実行前に表示し、利用者が承認した場合に限って続行する。

Git用語をUIへ露出する必要はない。利用者向け操作名は「別稿として書き直す」「版として残す」
「この稿を本稿にする」などとする。

### 4.6 化身（Occurrence）

実身をアウトライン、原稿、仮想ビューなどの特定文脈へ配置したものを表す。

```ts
interface Occurrence {
	id: string;
	workId: string;
	parentOccurrenceId: string | null;
	orderKey: number;
	collapsed: boolean;
	revisionSelector:
		| { mode: "branch"; branchId: string }
		| { mode: "pinned"; revisionId: string };
	contextualHeading?: string;
}
```

- Branch参照はそのBranchの最新版へ追従する
- Revision固定参照は引用、刊行稿、過去状態の再現に使う
- `contextualHeading`は同じ本文を原稿ごとに別見出しで置く場合だけ使う
- `contextualHeading`は初期実装に含め、化身固有の表示見出しとしてだけ扱う
- `contextualHeading`を変更しても実身本文、検索alias、Revisionは変更しない
- 原稿出力では`contextualHeading`を見出しに使い、未設定時は実身本文の表示ラベルを使う
- 化身の移動は配置だけを変更し、実身の系譜を変更しない
- 化身の削除は実身を削除しない
- 実身の削除は全化身とリンクに影響するため、別の強い操作とする

化身の子構造は配置ごとに完全独立させる。親子関係と表示順はOccurrence間の関係であり、
実身へ属する共有サブツリーを作らない。同じ構成を別の文脈でも使う場合は、同じ子実身を
それぞれの親化身の下へ明示的に化身として配置する。ある配置での移動、並べ替え、削除を
別配置へ波及させない。

同じ実身が自身の子孫位置へ再配置された場合、無限展開を防ぎ、再帰地点を参照スタブとして
表示する。

検索、Today、保存Queryが画面上に作る化身は一時的な投影であり、通常のOccurrenceとして
永続化しない。利用者が明示的に「化身として配置」を実行した場合だけ永続化する。

### 4.7 システム関係と意味関係

次の関係は利用者が意味リンクとして作るものではない。

- Revisionの親子
- merge parent
- 実身と化身
- 化身の親子と表示順
- タグ付与
- alias
- ブックマーク
- Knot / Stashへの内部所属

これらを意味リンクと同じ一覧へ混在させない。

### 4.8 削除とゴミ箱

削除は対象の違いをUI上で区別する。

1. **この化身を外す**: 選択した配置だけを削除し、実身と他の化身を残す
2. **実身をゴミ箱へ移す**: 実身をsoft deleteし、化身、Working Copy、Revision、Branch、
   タグ、alias、リンクを保持したまま通常ビューから隠す
3. **すべての履歴から完全に消去**: 影響範囲を表示して再確認した後、関連データを消去する

ゴミ箱からの復元では、化身の元の配置とリンクを可能な限り復元する。親化身が既に存在しない
場合は未配置箱へ戻す。ゴミ箱の内容は期間経過だけでは自動削除しない。

完全消去は実身本文、全Working Copy、Revision、Recovery Snapshot、Branch、化身、タグ、
alias、当該実身を端点とする意味リンクと内部参照を対象とする。完全消去の直前に対象本文を
含むRecovery Snapshotを新たに作らない。代わりに、件数とIDだけの影響manifestを残す。
利用者が別途JSONバックアップを選んだ場合を除き、完全消去後に本文を復元できると表示しない。

## 5. 型付き意味リンク

### 5.1 初期標準型

| 型 | 日本語 | 方向 | 用途 |
|---|---|---|---|
| `RELATED` | 関係がある | 対称 | 二項間の関係をまだ分類しない |
| `FROM` | ～から派生した | 有向 | 思索・作品の意味ある派生 |
| `LIKE` | ～と似ている | 対称 | 意味的類似 |
| `SUPPORT` | ～を支持する | 有向 | 根拠、裏づけ、肯定的論証 |
| `VS` | ～と対立する | 対称 | 緊張、両立困難、対立 |
| `FIX` | ～を修正する | 有向 | 先行主張の訂正・置換 |
| `CITE` | ～を引用・参照する | 有向 | 文献、資料、出典 |

現行の`IN`は利用者向け意味リンクから外し、Knot / Stashなどのシステム関係として保持する。

### 5.2 正準方向

保存時は主語・述語・目的語の順を正準とする。

```text
New FROM Old
A SUPPORT B
A FIX B
A CITE Source
```

`FROM`は意味上`New -> Old`だが、時間系統樹では年代順に`Old -> New`として描画してよい。
保存方向と描画方向を分離する。

有向型は逆方向の表示名を持つ。

| 正方向 | 逆方向 |
|---|---|
| ～から派生した | ～の派生先 |
| ～を支持する | ～に支持される |
| ～を修正する | ～に修正される |
| ～を引用する | ～に引用される |

### 5.3 リンクの状態

型と確度を分離する。

```ts
type LinkStatus = "provisional" | "asserted" | "retracted";
```

- `provisional`: 仮説的な関係。点線で描画する
- `asserted`: 利用者が採用した関係。実線で描画する
- `retracted`: 過去に主張したが撤回した関係。履歴から参照できる

リンクには作成日時、作成元（人間、提案、import）、任意の理由注記を保持する。
AIや検索が提示しただけの候補は採用済みリンクとは別エンティティにする。

### 5.4 Revision履歴と`FROM`の違い

- Revision parentは、どの版から編集を開始したかという機械的来歴
- `FROM`は、どの思索から派生したと意味づけたかという利用者の主張

誤字修正版は前版をRevision parentに持つが、全体系統樹で新しい`FROM`として強調する必要はない。
別稿を独立した実身へ昇格した時点で、元実身との`FROM`を作れる。

`FIX`もRevision parentとは独立しており、「Aから派生し、かつAを修正する」を同時に表せる。

### 5.5 ユーザー定義型

将来拡張できるデータ構造にはするが、初期UIでは標準7種に絞る。`CAUSE`、`EXAMPLE`、
`DEFINES`などを先回りして追加しない。ドッグフーディングで繰り返し不足する関係だけを検討する。

### 5.6 WorkリンクとRevision固定リンク

意味リンクの端点は原則としてWorkとする。Work間リンクはBranchやRevisionが増えても、
思索同士について利用者が主張した関係として存続する。

```ts
type LinkEndpoint =
	| { scope: "work"; workId: string }
	| { scope: "revision"; workId: string; revisionId: string };
```

- 通常のリンク作成とAdvanced Link EditorはWork間リンクを作る
- 特定の版にだけ成立する関係は、端点ごとに「この版に固定」を明示してRevisionを指定する
- Work端点とRevision端点を混在させることを許す
- Revision固定リンクは対象Revisionが変更不能であることを前提とし、後続Revisionへ自動追従しない
- Revision固定リンクも、そのRevisionが属するWorkのリンク一覧から参照できる
- UIでは固定された端点へ版名または作成日時のbadgeを付け、Work間リンクと見分けられるようにする

リンク型によって端点のscopeを制限しない。`FIX`や`CITE`以外でも、特定の異本にだけ成立する
関係があり得るためである。

## 6. 編集履歴、異本、Branch

### 6.1 「別稿として書き直す」

1. 「現在の内容を分岐点となる版として保存し、別稿を開始する」と事前表示する
2. 利用者が承認した場合だけ、現在のWorking CopyをRevisionとして確定する
3. そのRevisionから新Branchを作る
4. 新BranchのWorking Copyを別ペインで開く
5. 元のBranchと本文は変更しない
6. 元稿と新稿を並べてDiff表示できる

利用者が版保存をキャンセルした場合は分岐せず、現在のWorking Copyを維持する。
既に確定済みのRevisionから分岐する場合は新たなRevisionを作らない。

merge対象のBranchに未確定のWorking Copyがある場合は、先に各稿を「版として残す」よう求める。
未確定本文を黙ってRevisionへ取り込まない。Recovery Snapshotからの復元は過去内容を現在の
Working Copyへ再適用する操作であり、それ自体ではRevisionを作らない。

### 6.2 別稿完成後の操作

- **この稿を本稿にする**: `main`の先端を新稿へ進める
- **両方を残す**: 複数Branchを維持する
- **独立した思索にする**: 新しい実身を作り、元実身との`FROM`を作る
- **混成稿を作る**: 複数Revisionを親に持つRevisionを作る
- **破棄する**: Branchをarchiveする。Revisionは復旧可能な期間保持する

### 6.3 混成稿

初期実装では本文の自動mergeを行わない。

1. 利用者が親とする複数の確定Revisionと、編集の基準にする一稿を選ぶ
2. 基準稿の本文から新しいWorking Copyを作る
3. 他の親Revisionを二画面比較またはDiffで参照する
4. 利用者が必要な箇所を採録し、本文を手動で編集する
5. 「版として残す」で、選択した全Revisionを親に持つ`kind: "merge"`のRevisionを作る

未確定のWorking Copyを親へ暗黙採用しない。行や段落を選んで取り込む補助操作は提供できるが、
衝突解決や本文の意味的統合を自動確定しない。自動mergeはドッグフーディングで反復需要が
確認された場合だけ再検討する。

### 6.4 系統樹の解像度

全体表示では次を見せる。

- 実身
- 利用者が「全体系統に表示」を実行した重要Branch
- 明示的に昇格した重要な稿・版
- `FROM`、`FIX`、`VS`、`LIKE`などの意味リンク
- 複数親を持つ混成

Branchを利用頻度、経過時間、Revision数などから全体系統へ自動昇格させない。Work自体は
全体表示のノードになり得るが、`main`を別のBranchノードとして常時重複表示しない。
「全体系統に表示」を実行した時刻を`promotedAt`へ記録し、解除も可能にする。archiveされた
Branchは、利用者がarchive表示を有効にした場合だけ全体系統へ再表示する。

実身へズームした版系統では次を見せる。

- その実身のRevision
- Branch
- merge
- 版間Diff
- 作成日時
- 変更理由
- Recovery Snapshotへの入口

## 7. 採用する機能

### 7.1 ハッシュタグ

ハッシュタグは分類を確定する型ではなく、まだ型を決めたくない横断的な関連づけとして扱う。

- 本文中の`#タグ`を認識する
- 入力中に既存タグを補完する
- タグクリックで該当する実身を絞り込む
- 複数タグのAND検索と除外検索を提供する
- タグ一覧、使用件数、名前変更、統合を提供する
- アウトライン階層から子へ自動継承しない
- タグ自体を系統樹のノードやエッジにしない
- 同じタグを持つだけで`LIKE`を自動作成しない
- タグ一致は関係候補の根拠として利用できる

インラインタグはWork全体ではなく、記述されているWorking CopyまたはRevisionへ帰属する。
編集中のBranchの現在タグはWorking Copy本文から導出し、Revision確定時にはその時点のタグ集合を
Revisionとともに固定する。

- Work全体へ各Branchのタグを合成したcanonical tag setは作らない
- Branchの現在タグは、そのBranchのWorking Copyまたは先端Revisionのタグとする
- `main`と別稿が、それぞれ`#完成`と`#執筆中`を持つことを許す
- 通常のタグ検索はarchiveされていないBranchの現在タグを対象にする
- 検索結果は同じWorkを一件へまとめても、どのBranchで一致したかを併記する
- 過去Revisionのタグは履歴を検索対象に含めた場合だけ一致させる
- Revision固定の化身では固定Revisionのタグ、Branch追従の化身ではBranchの現在タグを表示する

将来、本文に現れない恒久分類が繰り返し必要になった場合だけ、インラインタグとは別の
Work metadataを検討する。

### 7.2 ブックマークと作業再開位置

「お気に入り」と「中断した編集の再開」を分ける。

- **栞**: 利用者が手動で残す恒久的な目印
- **作業位置**: 最後に編集していた化身とキャレット位置を自動保存する

栞を開いたときは、祖先を一時展開し、対象を画面中央へ移動して強調する。Treeでは対象時期へ
ズームする。栞は原則として特定の化身を指し、化身が失われた場合は実身を代替表示する。

### 7.3 Today仮想ビューと日付検索

専用Daily Noteや日付親ノードは作らない。

- 今日作成した実身を時系列表示する
- 今日編集した既存実身を別枠で表示する
- 本来の配置をパンくず表示する
- 前日、翌日、週、任意期間へ移動する
- `created`と`updated`を区別して検索する
- OutlineとTree上で日付範囲を強調する
- Todayから新規入力した思索は未配置の親なし実身として作る

### 7.4 Quick Capture / 未配置箱

- グローバルまたはアプリ内ショートカットで即座に入力する
- 配置先を要求せず、親なし実身として作る
- 未配置ビューから後で化身配置、リンク、タグ付与、統合を行う
- 作成日時を自動記録し、Todayビューへ反映する

### 7.5 Hoist、パンくず、閲覧履歴

- 任意の化身を一時的なルートとしてズームする
- パンくずから祖先へ戻る
- 戻る、進むの閲覧履歴を持つ
- 新しいタブまたはペインで開く
- 実身から全化身の配置一覧を開く

### 7.6 Sparse Outline

検索結果を平たい一覧だけで返さず、該当ノードと必要な祖先を残した疎なアウトラインとして
表示する。

- 一致した実身または化身
- 元の祖先文脈
- 直接リンク
- 必要に応じた系譜上の前後
- 検索順位の理由
- 日付、タグ、全文、型付きリンク、Queryに共通する表示方式

### 7.7 二画面比較

- `FROM`、`FIX`、`VS`、Revision親子の両端を左右に開く
- 各ペインは独立スクロールする
- 関係型、方向、作成日時、理由を中央またはヘッダーに表示する
- Revision間ではDiffを表示する
- 元稿を保ったまま別稿を編集する

### 7.8 Stub

検索やリンク作成中に、本文未記入の実身を先に作れる。

- Stub状態または`#stub`を付与する
- 作成元の文脈とBacklinkを保持する
- Stub一覧からその場で本文を補える
- 本文が追加されたらStub状態を解除できる

### 7.9 重複統合

- 自動判定は候補提示に限定する
- 統合前に本文、化身、リンク、Revisionを比較する
- 化身を選択した実身へ付け替える
- 旧名称を検索aliasとして残す
- 既存リンクと来歴を失わない
- 同一ではない場合は統合せず`LIKE`または`RELATED`を選べる

### 7.10 保存Query / 生きたアウトライン

既存の読み取り専用Datalog風Queryを、保存可能な仮想ビューへ発展させる。

- Queryに名前を付けて保存する
- 実行結果を一時的な化身投影としてアウトライン表示する
- 結果から実身を編集できる
- 結果は複製ではなく、再実行で更新する
- 栞またはショートカットから呼び出す

### 7.11 コマンドパレット

以下は製品としての目標仕様である。`Ctrl+K`などからノード操作を検索・実行できるようにする。

- 移動
- 化身として配置
- 型付きリンク作成
- トリプル入力で型付きリンク作成
- 別稿として書き直す
- 版として残す
- タグ付与
- 栞
- Hoist
- 原稿として開く
- Query実行

現行PoCのパレットは、Quick Capture、Hoistと解除、栞、確認付きの別稿作成、高度なリンク編集への
移動、Query実行・保存を共通の適用条件と無効理由で扱う。Outline内の追加、改行、階層変更、
並べ替えは本文入力中のキーボード操作として提供する。版として残す操作は復旧履歴の選択文脈から
実行する。化身としての配置、タグ付与、原稿として開く操作をパレットへ統合することと、
利用者がショートカットを変更する設定UIは将来拡張である。

現行PoCでは頻出操作に固定ショートカットを割り当てる。製品仕様では任意のショートカットを
割り当てられるようにし、マウス操作だけを前提にしない。

### 7.12 Advanced Link Editor

型付きリンクを、主語・述語・目的語の順に一行で入力できるようにする。
空白やタブはノード名に含まれうるため区切りには使わず、`::`を区切り記号とする。

```text
source :: TYPE :: target
```

```text
自由意志の再定義 :: FROM :: 従来の自由意志概念
観測結果 :: SUPPORT :: 仮説
新稿 :: FIX :: 旧稿
```

- 区切りはトップレベルの`::`二個だけとし、各フィールド外側の空白は除去する
- リンク型の入力は大文字・小文字を区別せず、保存時に標準型の大文字へ正規化する
- sourceとtargetは、実身の表示名、検索alias、短いIDを対象に補完する
- TYPE欄では標準リンク型と、その正方向の日本語表示名を候補表示する
- 現在選択中の実身から開いた場合、source欄をその実身で初期入力する
- 補完で確定したsourceとtargetは内部IDを持つトークンとして扱い、後の改名に影響されない
- 同名候補が複数ある場合は、パンくず、更新日時、短いIDを併記し、利用者が選ぶまで確定しない
- 解決できない名前からStubを作る場合は明示的に確認し、入力だけで暗黙作成しない
- 保存前に`source TYPE target`とリンク方向を自然文でプレビューする
- 三要素がすべて解決するまで確定操作を無効にし、どの要素が不正かをその場で示す
- 対称型では、sourceとtargetを入れ替えただけの重複リンクを新規作成しない

ノードの表示名そのものに`::`を含む場合は、そのフィールドを二重引用符で囲む。
引用符内では`\"`と`\\`をescapeとして扱う。通常は補完候補の選択によって
ID付きトークンへ変換されるため、利用者がescapeを手入力する必要はない。

```text
"A :: B" :: RELATED :: C
```

初期実装は一件のリンクを高速に作る単一行入力に限定する。複数行の一括作成は、
入力検証と差し戻しを設計した後の拡張候補とする。

### 7.13 長文と原稿ビュー

任意の化身を原稿の起点として開ける。実身から開始する場合は、どの化身配置またはBranchを
原稿として開くかを選ぶ。

- ノード本文をタイトル欄と本文欄へ強制分割しない
- Outline行では最初の非空行または冒頭を表示ラベルにする
- 原稿ビューでは配下の化身を順番に連続表示する
- 深さを見出しレベルへ投影する
- Outline側の並べ替えを原稿順へ反映する
- 原稿側から実身本文を直接編集できる
- 枝ごとの文字数と全体文字数を表示する
- 特定稿を固定して引用・採録できる
- Markdownへ一つの原稿として出力する

同じ実身を複数原稿へ配置しても、思索系譜は変更しない。原稿固有に全面改稿する場合は
新Branchまたは新実身へ分岐する。

### 7.14 Import / Export

| 形式 | 目的 |
|---|---|
| Markdown | 人間可読な原稿・アウトライン、Obsidianなどとの交換 |
| OPML | アウトライン階層の交換 |
| JSON | 実身、化身、Revision、Branch、リンクを失わない完全バックアップ |
| DOCX | 将来のWord受け渡し。初期必須ではない |

Markdown exportでは型付きリンクや稿情報の出力方法を選択可能にする。完全なRound-tripを
Markdown単独へ要求しない。

JSONバックアップと実DBのversioning規則は[[schema-evolution]]に従う。現行のversionなしJSONは
legacy schema version 0として読み取り、今後のexportは形式名とschema versionを持つ
envelopeへ移行する。

### 7.15 Markdown本文と内部参照

実身本文はCommonMark互換のMarkdownを基本とする。内部参照の正準保存形式には、表示名ではなく
不変IDを含む標準Markdownリンクを使う。

```markdown
[自由意志](radiora://work/0195...)
[初稿](radiora://revision/0195...)
```

- `radiora://work/<id>`はWork、`radiora://revision/<id>`は固定Revisionを指す
- 表示ラベルの変更は参照先IDを変更しない
- 内部参照はBacklinkを作るシステム関係であり、`RELATED`や`CITE`を暗黙作成しない
- 入力時は`[[`などから補完を開けるが、正準保存時にはID付きMarkdownリンクへ変換する
- 存在しないID、scopeとID種別の不一致、削除済み対象を区別して表示する

`radiora://`は初期実装ではアプリ内部の永続参照形式であり、OSのURL scheme handlerや
外部APIとしての登録を要件にしない。ただしURIの意味を後から変更せず、将来のRadiora CLI、
LLM agent、他アプリ連携が同じ識別子を利用できるようにする。外部から開く契約を公開する際は、
URI versioningと権限境界を別途定める。

インラインタグは、行頭または空白・句読点などの境界に続く`#tag`として認識する。

- 先頭文字はUnicodeの文字、`_`、または`-`とし、数字だけのタグは認識しない
- 続く文字にはUnicodeの文字・数字、`_`、`-`、`/`を許す
- `\#`はリテラルの`#`として扱う
- fenced code、inline code、MarkdownリンクのURL部分にある`#`はタグとして認識しない
- タグの帰属と検索範囲は[[#7.1 ハッシュタグ]]に従う

Markdown exportでは用途に応じて、`radiora://`を保持するRadiora向け、表示ラベルだけにする
portable向け、解決可能な参照を`[[表示名]]`へ変換するObsidian向けを選べるようにする。

## 8. 条件付き採用・保留

### 8.1 テンプレート

原稿構成、読書メモ、会議メモなどに有用だが、実身複製と化身配置の違いを明示できるまで保留する。

### 8.2 任意プロパティ

汎用Key-Valueデータベース化を避ける。出典、著者、確信度など、タグとリンクだけでは繰り返し
不足する属性が実使用で確認された場合に追加する。

### 8.3 ユーザー定義リンク型

データ構造上は拡張可能にするが、標準7種で不足する具体例が蓄積するまでUIを提供しない。

### 8.4 添付ファイルとWebクリップ

初期はURLとローカルファイルへのリンクに留める。PDF注釈、Webページ完全保存、画像管理は
別製品相当のスコープになるため保留する。

### 8.5 AI支援

候補提示、重複候補、検索補助、根拠の要約は検討できる。本文、系譜、リンクを自動確定しない。
AI生成物と人間作成物を明確に区別し、採用履歴を残す。

## 9. 原則として実装しない

### 9.1 汎用マインドマップ

中心から放射するだけの表示は実装しない。系統樹は生成時刻、派生、異本、型付きリンクを
読むための画面であり、同じ階層の別レイアウトではない。

### 9.2 全ノードの力学グラフ

全リンクを同じ重みで描く毛玉状グラフを主画面にしない。時間軸、系譜、関係型、選択文脈に
基づいて表示対象を絞る。

### 9.3 本格的なタスク管理

期日、繰り返し、通知、担当者、カンバン、カレンダー同期を中核へ入れない。状態の表現は
当面タグで行う。単純なチェック状態の必要性は実使用後に判断する。

### 9.4 フラッシュカード・間隔反復

思索の伝承と改稿を扱う目的から外れるため実装しない。

### 9.5 Word級の組版

フォント管理、余白、ページ番号、脚注配置、変更承認、差し込み印刷などを実装しない。

### 9.6 リアルタイム共同編集

単独利用の実身・化身・Branch整合性を先に完成させる。共有、権限、競合解決は本書の
実装フェーズに含めない。

### 9.7 AIによる自動執筆・自動整理

来歴の信頼性を損なうため、利用者の確認なしに本文、化身配置、系譜、意味リンクを生成・確定しない。

## 10. 実装段階

### Phase 0: 現行PoCの基準化

- 現行DBと`OutlineItem.parentId`の利用箇所を列挙する
- データ移行とロールバック方針を定める
- 現行DBとversionなしJSONをschema version `0`としてfixture化する
- [[schema-evolution]]に従うmigration runnerとschema metadataを導入する
- `FROM`の保存方向と描画方向をテストで固定する
- 既存データを失わないfixtureを作る

### Phase 1: 実身・化身と関係分離

- Work、Occurrenceを導入する
- アウトライン配置をOccurrenceへ移す
- 意味リンクをWork間関係へ移す
- Revision固定可能なLinkEndpointを導入する
- `IN`をシステム関係へ移す
- 新標準リンク型と状態を導入する
- `contextualHeading`と配置ごとに独立した子構造を導入する
- 化身削除、実身のゴミ箱、完全消去を分離する
- 現行データを移行する

完了条件:

- 同じ実身を複数箇所へ置き、どこから編集しても本文が一致する
- 化身の移動で`FROM`が変化しない
- 化身削除と実身削除が別操作になっている
- 循環配置で無限展開しない
- 一つの配置での並べ替えが別配置の子構造を変えない
- ゴミ箱から化身、Revision、リンクを含めて復元できる

### Phase 2: Revision、Branch、異本系統

- Working CopyとRecovery Snapshotを導入する
- Revision、Branch、複数親を導入する
- 別稿作成、版確定、比較、本稿切替、独立化を実装する
- 明示的なBranch昇格と手動の混成稿作成を実装する
- Node Diffを実装する
- 全体系統と版系統の表示を分ける

現行PoCではstorage／service境界、版系統と全体系統の読み取り表示、任意2版の比較、
既存Recovery Snapshotの差分確認・復元・Revision昇格まで到達している。明示的な版保存、
Branch lifecycle、手動merge、Snapshot自動生成・間引きはservice／policyと自動テストまでで、
UI導線とruntime接続は後続課題である。以下は製品としてのPhase完了条件を示す。

完了条件:

- 元稿を変更せず全面改稿を開始できる
- 二つの稿を並行編集できる
- Revision間Diffを表示できる
- 重要稿だけを全体系統へ表示できる
- 混成稿が複数親を保持できる
- 未確定Working Copyを暗黙にRevisionまたはmerge親へ取り込まない

### Phase 3: 入力とナビゲーション

- ハッシュタグ
- 栞と作業再開位置
- Today仮想ビュー
- Quick Capture / 未配置箱
- Hoist、パンくず、履歴
- コマンドパレット
- Advanced Link Editor（`source :: TYPE :: target`）
- `radiora://`内部参照の補完、解決、Backlink
- 二画面比較
- Markdown記法を確認しながら編集する通常表示、プレーン入力、読み取り専用プレビュー

現行PoCでは、上記をサービス境界とUIへ接続している。主要な作成・階層変更・並べ替え・
別稿作成・リンク入力はキーボードから開始できる。Advanced Link Editorは三要素がすべて
解決するまで確定できず、未解決名からWork、Occurrence、Stubを暗黙作成しない。
Markdown入力はOvertype 2.4.0を交換可能なアダプター境界で利用し、初期化できない場合は
textareaへ戻す。画像、表、分割プレビューは初期採用範囲に含めない。

### Phase 4: 検索と知識整備

- Sparse Outline
- 保存Query / 生きたアウトライン
- Stub
- 重複候補と安全な統合
- タグやリンクを根拠にした発見候補の改善

Phase 4では上記を現行PoCへ接続した。検索・Today・保存Queryは永続Occurrenceを作らない一時投影
として扱い、Stub作成、重複統合、候補からの意味リンク採用はいずれも利用者の明示操作に限定する。
発見候補は確定リンクと別エンティティとして、採用・却下・保留と根拠を追跡する。

### Phase 5: 長文と可搬性

Phase 5以降は次段階の実装範囲である。

- 原稿連続表示
- 文字数と構成確認
- Markdown export
- OPML import / export
- JSON完全バックアップとrestore検証
- backup schema versionとversion `0`からのmigration検証

### Phase 6: ドッグフーディング

Phase 0から5を完了した後、一定期間Radioraを次の用途で実際に使う。

- 日々の着想のQuick Capture
- 既存思索の改稿とBranch
- 対立、支持、修正、出典リンク
- 長文の構成とMarkdown出力
- 過去稿の検索と系統閲覧

改善候補ごとに、再現例、頻度、回避策、データ量、期待結果を記録する。単に他製品に存在する
ことを理由に新機能を追加しない。

## 11. 横断的な受け入れ条件

- 既存データを失わず移行できる
- すべての破壊的操作に対象と影響範囲が表示される
- 実身削除、Branch破棄、Revision復元を取り違えない
- DB migration失敗時に旧データとschema versionを不整合な状態で確定しない
- OutlineとTreeで同じリンク方向を一貫して説明できる
- キーボードだけで主要な作成、移動、リンク、分岐ができる
- トリプル入力で空白を含む日本語名、同名候補、リテラルの`::`を誤解釈しない
- トリプル入力の型やノードが未解決な場合、リンクやStubを暗黙作成しない
- 高密度データでも選択文脈を見失わない
- AIまたは自動提案と、人間が確定した関係を識別できる
- Markdown、OPML、JSONの文字コードと日本語本文が往復で壊れない
- 生成物、診断ファイル、テスト出力をコミット対象にしない
- 各実装単位の完了前に`cd v2 && deno task verify`を成功させる

## 12. 確定した初期方針

### 12.1 設計上の決定

1. Recovery Snapshotは[[#4.3 Recovery Snapshot（復旧スナップショット）]]の初期既定ポリシーを
   採用する。ポリシーは内部で差し替え可能にし、実測により改訂する
2. Revisionは明示的な版保存でのみ作る。分岐など固定Revisionが必要な複合操作では、
   版保存を事前表示し、利用者の承認後にだけ実行する
3. 化身の子構造は配置ごとに完全独立させ、実身へ共有サブツリーを持たせない
4. 意味リンクは原則Work間とし、特定の版にだけ成立する端点を明示的にRevisionへ固定できる
5. `contextualHeading`は初期実装へ含め、化身固有の表示見出しに限定する
6. Branchは利用者が明示的に昇格した場合だけ全体系統へ表示する
7. 混成稿は複数親を記録するが、初期実装では本文を手動で編集し、自動mergeしない
8. Markdown内部参照は`radiora://`の不変IDを持つ標準Markdownリンクとして保存する。
   タグとescape規則は[[#7.15 Markdown本文と内部参照]]に従う
9. 通常の実身削除はゴミ箱へのsoft deleteとし、完全消去を別の強い操作にする
10. DBとJSONバックアップは別々の整数schema versionを持ち、[[schema-evolution]]の規則で
    migrationする
11. インラインタグはBranchの現在のWorking CopyまたはRevisionへ帰属させ、Work全体へ
    無条件に合成しない

### 12.2 変更管理

本書で挙げた未決事項はすべて初期方針を確定した。各値やUI細部は実装時に決めるが、
上記の責務分離を変更する場合は本書とschema migration計画を先に更新する。

実装上の都合だけを理由に、配置と系譜の分離、復旧履歴と意味ある版の分離、日付を親に
しないという中核判断を後戻りさせない。
