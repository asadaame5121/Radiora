## 1. 提供資料で明示された決定

| 対象 | 決定 |
| --- | --- |
| 文書 | 最上位ブロックとその子孫を一つの文書とする |
| タイトル | 最上位ブロック自体を文書タイトルとして扱う。別のタイトル入力を必須にしない |
| Topicルート | 最上位ブロックが兼ねる。子孫なしでも本文が空の文書として扱える |
| 編集 | アウトライナーUI、Tab、Enter、階層変更、折りたたみ等を維持する |
| 内部参照 | 文書全体だけでなく文書内のブロックを参照できることが必要 |

ルートのTabや最上位へのアウトデント等、文書境界を変えるケースの具体的な挙動まで決定したものではない。
安定したブロックIDは実現候補だが、ID形式・同一性・URL形式は未決。
`[[フロイト]]` 等の表記例も確定した入力構文ではない。

## 2. 理由と設計原則

- **文書＝知識のまとまり、ブロック＝編集・参照単位、アウトライナー＝編集インターフェース**を分ける。
  行の分割位置に独立した知識の同一性まで背負わせない。
- 通常の階層編集を内容共有・複数配置の同一性から切り離して考える。
  共有や埋め込みは具体的な用途から判断し、既存共有機能を勝手に廃止しない。
- 本文の親子関係と、文書間の関連・派生・版系統は別物。
  インデントや移動だけで意味関係・派生・Revisionを自動生成する仕様にはしない。
- 文書化とアウトライナー編集の廃止は別。通常の段落エディタへの置換を前提にしない。
- 原稿ビューを同じ文書の別表示・編集形式として扱う案は候補。
  表示、双方向編集、内容を変える生成処理はそれぞれ別の判断。

## 3. Work / Occurrence / Loroとの関係

**Topic＝Work、文書＝Work、ブロック＝Occurrenceという一対一対応は未決定。**
既存の役割を調べ、新しい用語への単純な置換で済ませない。
必要な共有・配置・履歴の用途が残るなら、その用途へ旧概念を限定する案を検討する。
複数配置の旧データを独立コピーへ変えて共有編集を失わせてはならない。

LoroのSSOT採用は保存技術の方針であり、この文書の製品モデルを自動的に決めない。
[Loro対応案](loro-backend-migration-research.md#31-現行モデルからloroへの対応案)は旧データ互換の候補であり、
新製品schemaの確定ではない。全体1 doc / 文書ごとdoc、blockごとの本文、
Topic専用record/IDの要否は、境界操作・参照・共有の判断から決める。
内容ハッシュを安定参照IDとして採用することも決めていない。

保存技術のPoCは最小fixtureで先行可能だが、目標schemaを使う変換readerや破壊的変換は以下の判断を待つ。
旧Work/Branch/Occurrence/Revision等のID・値・関係は移行元の保護対象とし、
新版に同じentityを永久に残す要件とは区別する。

## 4. 実装前に固定する境界

| 判断 | 確定すべきこと |
| --- | --- |
| 文書境界 | 保存構造上のrootと画面上の先頭を区別。ルート移動/Tab、内部blockのアウトデント、タイトル上/空タイトル上/末尾のEnter |
| 分割・統合 | 機能の採否、タイトル/所属/付随情報/履歴/undo/既存参照の引継ぎ。単なる表示整理との区別 |
| 同一性・参照 | IDの一意性範囲、生成、移動/複製/削除/復元/undo時の継承。Topic IDとroot block IDの兼用/分離 |
| 旧データ | 多重配置、共有内容、孤立Work、pinned、旧Work/Revisionリンクの解決。対応不能ケースの明示と保全 |
| 表示状態 | 折りたたみを文書/配置/ユーザー/画面のどこへ保存するか。ズームを採るなら表示範囲と所属文書を区別 |
| 入出力 | コピーは移動と同一視しない。新ID、内部参照の再対応、import衝突、export時の参照保持 |
| 関係・版 | 通常linkと型付きRelation、文書間派生、同文書の版、block履歴の役割と粒度 |
| 原稿ビュー | 別表示案の採否。編集可能にするなら段落/見出し/階層/参照/undoの往復対応 |

すべての候補機能を初回に実装する必要はない。
初回に提供しない境界操作は明示的に対象外/禁止とし、未決の意味を旧操作へ黙って割り当てない。
旧リンクが指す内容を任意の別blockへ解決して成功扱いしない。

## 5. 移行計画への組込み

原本の段階案は、依存調査→旧構造上で文書として読める表示→安定参照→境界操作→保存経路→不要旧概念の削減。
これは実装前の提案であり、全工程の現行版への先行実装を要求するものではない。

現行版凍結・Tauri/Loro計画とは次のように整合させる。

1. 現行の共有・配置・リンク・履歴・設定・入出力と固定fixtureを棚卸しする。
2. コピー/fixtureの読取り投影で「root＋子孫＝文書」を検証する。保存形式を変えず検証できる範囲を使う。
3. 初回の文書境界、ID/参照、旧共有の移行規則を決め、[#290](https://github.com/asadaame5121/Radiora/issues/290)、
   [#286](https://github.com/asadaame5121/Radiora/issues/286)等の契約と対応付ける。
4. 保存技術PoCの結果と合わせてdoc/container/schemaを選び、旧DBから別DBへ変換・再起動検証する。
5. 新版UIへ接続する。旧モデルを残す互換部分と新モデル部分のwriter/正本を明示し、dual-writeを増やさない。
6. 参照・共有・履歴の代替と利用結果を確認した後だけ、不要になった旧経路を別判断で撤去する。

## 6. 必須回帰と後続候補

空/同名タイトル、深い階層、タイトル変更、本文編集、並べ替え、再読込、
文書内/文書間の内部block参照、削除/復元/複製、旧リンク、共有内容・多重配置、
移行中断/再実行/backup復元を試す。件数一致だけでなく、内容・階層・順序・参照・共有の意味を比較する。
文書境界の変更を採る場合は、所属・ID・参照・付随情報・undoをセットで試す。
ズーム・埋め込み・双方向原稿編集・系統樹再設計は採用された範囲だけ検証する。
今回の追加では、これらの実装・回帰試験・既存データ変換を実行していない。
